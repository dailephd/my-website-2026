Architecture discipline

- `src/types` defines shared types and interfaces.
- `src/content` holds structured local content records.
- `src/lib/content` adapts, normalizes, and validates content.
- `src/lib/seo` builds metadata and structured data helpers.
- `src/components/ui` contains reusable primitives.
- Feature components render passed content through props.
- `src/components/layout`, `src/components/theme`, and `src/styles` own shell and theme behavior.
- `src/app` composes pages, metadata, sitemap, robots, and route-level behavior.
- Lower layers must not import higher layers.
- Content modules must not import React components.
- UI primitives must not know about project-specific content records.

my-dev-kit retrieval workflow

Use the published, version-pinned my-dev-kit package already installed under
`.my-dev-kit-workflow/tools/mdk` (the local package manifest records its version). Do not use a
separate checkout unless the task explicitly targets my-dev-kit package development. Keep the
index, slices, caches, and other task output under `.my-dev-kit-workflow/` or `.my-dev-kit-context/`.

Use source roots that actually exist. Expected roots after scaffold:

- `src`
- `tests`
- `docs`
- `scripts`

Suggested index command:

`node ".my-dev-kit-workflow/tools/mdk/node_modules/@dailephd/my-dev-kit/dist/cli.js" index --root "." --src "src" --src "tests" --src "docs" --src "scripts" --out ".my-dev-kit-workflow/indexes/current" --call-graph --json`

If a source root does not exist yet, inspect the repo and adjust the command. Do not invent directories.

Preferred retrieval order

1. index
2. search
3. lookup
4. slice
5. exact source
6. line-range source
7. full-file read only if needed

Examples

Search:

`node ".my-dev-kit-workflow/tools/mdk/node_modules/@dailephd/my-dev-kit/dist/cli.js" search --index ".my-dev-kit-workflow/indexes/current" --query "RoadmapPreview roadmap status" --limit 20 --json`

Lookup:

`node ".my-dev-kit-workflow/tools/mdk/node_modules/@dailephd/my-dev-kit/dist/cli.js" lookup --index ".my-dev-kit-workflow/indexes/current" --node "<node-id>" --depth 1 --json`

Slice:

`node ".my-dev-kit-workflow/tools/mdk/node_modules/@dailephd/my-dev-kit/dist/cli.js" slice --index ".my-dev-kit-workflow/indexes/current" --node "<node-id>" --depth 2 --direction both --out ".my-dev-kit-workflow/indexes/task-slice.json" --json`

Source:

`node ".my-dev-kit-workflow/tools/mdk/node_modules/@dailephd/my-dev-kit/dist/cli.js" source --index ".my-dev-kit-workflow/indexes/current" --node "<symbol-node-id>" --max-lines 160 --format numbered`

Testing expectations

For meaningful code changes:

- identify assumptions before implementation
- identify realistic failure modes
- add unit tests for pure logic
- add integration tests for content adapters, route/page composition, or contract boundaries where applicable
- add E2E tests for user-visible workflow guarantees where applicable
- do not require internet access in normal tests
- do not claim tests passed unless they were run

For documentation-only changes:

- run `git status --short --untracked-files=all`
- list changed files
- run the fastest available checks
- do not modify production code unless needed for documentation consistency

For infrastructure or script changes:

- verify scripts exist in `package.json`
- verify documented commands match actual scripts
- run `npm run dev:check` if available
- do not leave long-running services running
- document environment blockers separately from code failures
